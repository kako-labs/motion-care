# 운행 비교 요약 문구 개선

기준 커밋 `4b37cc0`, 작업 브랜치 `feat/history-approved-compose-ui`. `docs/handoff.md`의 비교 요약 후속 항목을 구현했다.

## 사용자에게 보이는 변화

- 패턴 이름을 먼저 밝히고 `이번 운행 1.3회/10분 · 이전 2회 평균 2.1회/10분`처럼 같은 단위의 비교를 한 문장으로 묶었다.
- 비교 기준은 **같은 운전자의 이번 분석 대상보다 앞선 완료 운행 중 분석 가능한 N회**라고 표시한다. `가장 최근 운행`이라는 모호한 숫자 제목은 제거했다.
- 실제 관찰 횟수·운행 시간·유효 분석 시간·계산식은 `실제 횟수와 계산 방법`을 펼쳐서 본다. 계산에는 반올림 전 시간을 쓰며 표시에만 반올림한다.
- 이전 자료가 없으면 `이전 운행 없음`으로 표시한다. 분석 부족은 0회로 바꾸지 않는다.
- HTML 설명 본문의 고정된 `이전보다 낮았어요`도 수정했다. 높음·같음·이전 없음에 각각 맞는 설명을 한다.
- 운전 패턴 관찰 빈도이며 멀미가 줄었다는 뜻이 아님을 분리해 적었다. 감소율이나 의학적 점수는 추가하지 않았다.

## 유지한 범위

집계·조언 선정·저장·ViewModel·Repository·탐지·내비게이션은 변경하지 않았다. Android는 기존 최근 최대3회 중 이번 운행을 제외한 최대2회, HTML은 기존 이전 최대3회를 비교한다. 상한을 임의로 통일하지 않고 실제 비교 건수 N을 표시한다. 향후 상한을 통일하려면 별도 정책 검토가 필요하다.

비교 문구 구현 범위(`4b37cc0..236661e`)에서는 `app`, `core`, `data`, Gradle, SDK, 서비스, 공통 계약 및 DB 변경이 없다. 이후 `682e8bc`에서는 앱 통합 테스트의 기대 문구만 바로잡았다. 이전 승인 Compose UI·속도 분석 확장은 선행 커밋의 작업이다.

## 근거와 확인 수준

- 요구: [인수인계](../handoff.md)의 기록 화면 문구 후속, [최신 기획](../proposal.md)의 분석/해석 원칙.
- 팀 Notion의 `확정 B 화면 · 다른 노트북에서 열기 · 그래프 읽는 법` 중 10분당 빈도·이전 비교·멀미 감소와의 구분을 읽고 대조했다. 팀 연구/기획의 의미를 바꾸지 않았다.
- 데이터 근거: `AdviceViewModel`, `AdviceRoute`, `adviceContext`가 실제로 제공하는 완료/분석 가능 운행과 기존 빈도. 새 의학적 근거가 필요한 수치·주장은 만들지 않았다.
- 한 문장으로 비교하고 계산식을 접는 표현 방식은 인계 요구에 따른 구현 판단이며, 사용성 효과를 실험으로 입증한 결과는 아니다.

## 검증

- `python scripts/dev.py verify` 최종 성공: 빌드·의존성·lint·단위 검사 **280개 / 33 suite**, 실패·오류0.
- 새 Kotlin 복사 모델 검사4개: 비교 구분·실제 횟수/분석 시간·이전 없음·현재 분석 부족·실제 비교 건수·기기 로케일과 무관한 소수점 표기. 구현 전 unresolved helper 실패를 확인하고 구현 후 통과했다.
- HTML 기존 회귀 파일4개 통과. 비교·본문의 높음/같음/이전 없음도 회귀 검사에서 실패 후 수정해 통과했다.
- HTML1600/1024/390 너비에서 접힘·펼침 실제 클릭, 가로 넘침 없음. 같은 j1의 두 번째 감속에서 해당 기록/사건으로 이동하는 흐름 유지 확인.
- 일반 Android API35의 **읽기 전용 테스트 에뮬레이터**에서 격리 debug fixture를 사용해1024×768 접힘/펼침,768×1024 재배치 후 비교 문구를 확인했다. 실제 사용자 DB 주입·실차 검증은 아니다. UI 계층 덤프의 초기 부팅 지연은 준비된 화면을 기다려 해결했다.
- 독립 최종 코드 리뷰 및 추가 본문 수정 리뷰에서 Critical/Important 없음.

UI/수명 흐름은 바꾸지 않았으므로 기존 앱 instrumentation 소스는 수정하지 않았다. 원격 검사는 PR Checks에서 해당 커밋 기준으로 확인한다.

## 원격 CI 결과와 통합 담당 후속

커밋 `236661e`의 [원격 실행 42610475440](https://github.com/kako-labs/motion-care/actions/runs/42610475440)은 verify 성공, UI 5개 중4개 성공·1개 실패다. 전체 성공으로 처리하지 않는다.

실패는 `ScaffoldFlowTest.profileScreenReadsTheProfileStoreAndReturnsHome`의31행이다. `출발 전 안내` 도착 후 기존 `운전자 0 · 동승자 0` 문구를15초 기다리다가 만료했다. 인수 기준 `4b37cc0`의 `ReadyContent.kt`도 이미 `탑승 인원 0명`과 좌석 선택 안내를 표시하며 이전 문구는 없다. 이번 후속은 해당 화면·테스트를 변경하지 않았다. 타임아웃을 늘려도 없는 문구는 나타나지 않는다.

초기에는 [검토용 패치](scaffold-empty-seating-test.patch)로 준비했으며, 후속 사용자 지시에 따라 `app`의 해당 테스트에 적용했다. 빈 좌석 상태의 현재 인원수와 안내를 확인하도록 기대값만 맞췄다. 기존 탐색·뒤로 이동 검사와15초 제한은 유지한다. 앱 동작·DB·내비 계약 변경은 없다. 실패 근거는 위 원격 실행에 있으며, 수정 후 UI 재검증 결과는 PR Checks에서 해당 커밋을 확인한다. 패치는 적용 내역 참고용으로 보존한다.

수정 커밋 `682e8bc`의 [원격 실행 42613567634](https://github.com/kako-labs/motion-care/actions/runs/42613567634)는 **verify·UI 모두 성공**했다. 로컬 필수 `python scripts/dev.py verify`와 읽기 전용 API35 테스트 에뮬레이터의 `python scripts/dev.py ui-connected`도 성공했고 UI5개 모두 실패·오류·생략0이다. 최초 로컬 UI 시도는 검사 시작 전 ADB 연결 초기화로 중단되었으며, 기기 재연결 확인 후 동일 코드로 재실행해5개 통과했다. 테스트 기기는 종료했다. 팀원이 별도로 패치를 적용할 필요는 없으며 PR 리뷰·통합 판단만 남는다.
